# Ushahidi v19.0 migration evidence

## Source decision

Debian Trixie does not package Ushahidi. The appliance installs the official
Ushahidi Platform v6.0.17 release archive and binds it to official tag commit
`8b50289a360cd6a17d64f663dd7ec68369863f2f`, archive SHA256
`9dd9fdfdb563400d0bdc2ba991a2552661541c304c4cadfd79c29539315a8e4e`, and
Composer lock SHA256
`cf38243e034da38b939ef548d8acd0531f26a8b5676d747b29d028000992440c`.
That digest identifies the unmodified upstream archive. The installed lock is
then updated coherently with the Laravel runtime and recorded separately.

The release's API requires PHP `>=7.4 <8`. Debian Trixie's supported default is
PHP 8.4, so Debian cannot provide a compatible PHP runtime. TurnKey prefers a
Debian-supported package whenever one satisfies the application contract. In
this last-resort case, the appliance selects PHP 7.4 from the deb.sury.org
Trixie repository. This is consistent with Ushahidi v18, which also used Sury
for the old PHP line needed by upstream.

The Sury route is third-party, best-effort maintenance. Its maintainer says old
PHP versions are supported while feasible and directs consumers who require a
defined SLA to a commercial LTS service. TurnKey therefore does not represent
this source as having a guaranteed coverage window. Repository availability,
signature identity, installed origin, version, and recent backport evidence are
part of the v19 acceptance test so a material source change fails visibly.

Ushahidi v6.0.17 originally locks Laravel Framework v8.83.27. Laravel 8's
formal security window ended on 2023-01-24, but its official 8.x Git history
has received later maintenance: upstream backported the CVE-2024-52301 fix in
commit `eded6bdfc05af9b5437d107b4d092558fe46292c`, released it in v8.83.28,
released v8.83.29 at commit
`d841a226a50c715431952a10260ba4fac9e91cc4`, and continued 8.x branch work in
2025. Under the recorded last-resort policy, TurnKey accepts this official
upstream history as a best-effort source with no guaranteed coverage window.
It is not represented as formal Laravel support or as assurance that every
advisory will receive an 8.x backport.

The appliance updates the shipped runtime to v8.83.29 and retains a complete
bare copy of `https://github.com/laravel/framework.git` at
`/usr/local/share/turnkey-ushahidi/laravel-framework.git`. It retains only the
8.x branch and v8 tags, but includes all objects needed for shipped-version
recovery and the offline fixture. The exact tag, commit, tree, remote, security
baseline, framework manifest, installed Composer metadata, and lock digests are
recorded in `/usr/local/share/turnkey-ushahidi/laravel-runtime`.

## Sury repository provenance and pinning

`PHP_VERSION=7.4` activates TurnKey common's `bootstrap_apt` Sury integration.
It installs the keyring package from
`https://packages.sury.org/debsuryorg-archive-keyring.deb`, writes a deb822
source restricted to suite `trixie`, and binds that source with `Signed-By` to
`/usr/share/keyrings/debsuryorg-archive-keyring.gpg`.

The keyring retrieved on 2026-08-27 was package version `2025.11.18`, SHA256
`7511384559c9ddf1d5ce5f60be429ae9d4e7d01d9480d6f1b7a30c0810cf8b60`, with
primary fingerprint `15058500A0235D97F5D10063B188E2B695BD4743`. The test pins
the fingerprint, not the mutable keyring-package checksum, so intentional key
rotation requires explicit review.

APT gives all packages from `packages.sury.org` priority 10 and gives only the
exact installed runtime closure (`php7.4-*`, `libapache2-mod-php7.4`,
`php-common`, `mlock`, `libc-client2007e`, and `libgd3`) priority 550. This lets
every installed Sury dependency receive ordinary upgrades without allowing
unrelated Sury packages to displace Debian packages. The package's global apt
trust copy is removed; only the key named by this source's `Signed-By` remains.
Debian remains preferred for Apache, MariaDB, Redis, Postfix, and the rest of
the operating system. The appliance rejects any installed PHP 8+ runtime or
Apache module, rather than checking one PHP 8.4 package name.

The live Trixie index observed on 2026-08-27 published these relevant versions:

| --- | --- |
| `php7.4-cli`, `php7.4-common`, `php7.4-mysql`, `libapache2-mod-php7.4`, and bundled extensions | `1:7.4.33-30+0~20260703.120+debian13~1.gbp1cce3b` |

`/usr/local/share/turnkey-ushahidi/php-runtime` during the build and compared
with `dpkg-query` by `tests/v19.sh`.

## Security-update evidence and channels

The Sury PHP 7.4 Debian changelog demonstrates post-upstream-EOL backport work,
including:

- `7.4.33-30` (2026-07-03): an OpenSSL encryption memory-corruption fix
  backported from PHP 8.2.32.
- `7.4.33-27` (2026-05-13): six named 2026 CVE backports, including
  CVE-2026-6735, CVE-2026-7261, and CVE-2026-7262.
- `7.4.33-24` (2025-12-18): CVE-2025-14177, CVE-2025-14178, and
  CVE-2025-14180 backports.
- `7.4.33-13` (2024-06-06): a CVE-2024-5458 backport after upstream PHP 7.4
  support had ended.

PHP fixes arrive through the normal signed Sury APT channel. Administrators can
refresh and apply them with `apt-get update && apt-get upgrade`; the ordinary
TurnKey package-update mechanism sees the same channel. There is no separate
application-local PHP patch set.

`turnkey-ushahidi-update` handles Ushahidi itself. It discovers only published,
non-prerelease v6.0 patch releases, but discovery is not trusted. Apply requires
the candidate's tag commit, release-archive SHA256, and Composer-lock SHA256 to
match a release tuple embedded by a reviewed TurnKey package update. A newer
unvetted upstream release fails closed. Its non-mutating commands are
`turnkey-ushahidi-update --check` and
`turnkey-ushahidi-update --apply --dry-run`.

`turnkey-ushahidi-laravel-update` is deliberately separate. It fetches the
official 8.x branch and `v8.*` tags into the packaged Git repository, but
selects only stable `v8.N.N` tags. It rejects prereleases, other major lines,
downgrades, unrelated history, candidates outside official 8.x, tags preceding
the CVE-2024-52301 baseline, tag/runtime-version disagreement, and changes to
the Laravel dependency or autoload contract. A candidate is exported to a new
immutable generation; it is never pulled or overlaid onto live vendor files.

The framework, Composer lock, `installed.json`, and `installed.php` resolve
through one generation link. Apply switches that link only after staging,
integrity validation, focused PHP lint, and package checks. It runs a live
Artisan version check after activation and automatically restores the prior
generation on failure. `--rollback` exchanges the two verified generations and
also restores the original if rollback health validation fails. The supported
administrator commands are:

```sh
turnkey-ushahidi-laravel-update --check
turnkey-ushahidi-laravel-update --apply --dry-run
turnkey-ushahidi-laravel-update --apply
turnkey-ushahidi-laravel-update --rollback
```

If official stable 8.x tags stop, a tag is unrelated, or its package contract
changes, the command stops. TurnKey must then review/backport the issue,
provide a reviewed updater revision, migrate Ushahidi, or withdraw the affected
path; administrators must not substitute branch HEAD or an unverified fork.

## Deferred issues

- **RESOLVED POLICY DECISION:** Laravel formal support has ended, but TurnKey
  accepts the official 8.x Git history as the no-SLA, best-effort source. The
  appliance ships v8.83.29, the CVE-2024-52301 baseline, the complete scoped Git
  repository, and a stable-tag-only fail-closed updater. TuxCare credentials or
  redistribution authority are not required for this selected path.
- **RESOLVED BUILD INPUT:** the exact run used clean common candidate
  `9cf391e42aca6e6ee55c2ba36223ce2e89830bfa` (tree
  `27715a34a5cab0213b7ca43510f24b71d14987c6`), which authenticates Sury key
  material before package execution. The appliance removes global trust and
  narrows the final runtime pin closure.
- **REVIEW GAP:** the Laravel updater has a real offline v8.83.28→v8.83.29
  apply/rollback fixture. A real Ushahidi application updater transition from
  v6.0.16 to v6.0.17 remains unattempted; the two channels are intentionally
  separate and a future Ushahidi tuple is rejected if non-Laravel Composer
  dependencies drift without a TurnKey reconciliation.

- MEDIUM: PHP 7.4 is upstream-EOL. Sury is actively backporting fixes, but its
  best-effort policy has no coverage guarantee or fixed end date. If its Trixie
  PHP 7.4 channel stops receiving fixes, TurnKey must reassess Ushahidi rather
  than silently retaining the last package.
- MEDIUM: Laravel 8 has no guaranteed coverage. Official post-EOL stable tags
  are accepted best-effort, but future advisories may require a TurnKey
  backport, an Ushahidi migration, or withdrawal when upstream does not act.
- LOW: Acceptance uses the same OAuth and API calls as the browser client
  rather than automating every screen. It covers authentication and the
  identity-defining survey/post workflow without a browser fixture.

## Loop accounting

Only a source change intended to fix a reproduced defect that materially breaks
a documented supported main flow, security or integrity, or the update path
consumes one of six product loops. Build, test, evidence, harness, and
infrastructure corrections consume zero. The product ledger is frozen at six
of six: MariaDB service-state recovery, valid application-key generation,
Apache service-state recovery, the approved Laravel Git-channel integration,
semantic Laravel package-identity validation, and runtime-readable Laravel
generation roots. Literal pin matching, APT policy parsing, and normalized
locale expectation corrections were test-only corrections and consumed zero.
